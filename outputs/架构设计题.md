# 架构设计题
## 一 Context / Performance

**问：大模型面对第一轮长窗口或多模态输入时，first token 会显著变慢。有什么快速、低成本、用户体验也不差的方案？如何从 5～10 秒稳定压缩到 2 秒？**

**答：**可以从缩减输入、并行前置处理、缓存复用和请求路由四个方面优化，并通过流式输出改善等待体验。首先需要拆分耗时，确认瓶颈位于上传与传输、排队、上下文组装、多模态编码、模型预填充计算（prefill），还是客户端缓冲。如果回答依赖工具，还需要统计模型决策、工具执行及后续生成的时间。模型首 token、首段有效回答和进度提示应分别计时。

第一，减少首轮实际输入。精简系统提示，工具和 Skill 按需加载，对检索片段去重，只保留与当前问题有关的内容。局部文件问答采用分块检索，全篇总结采用覆盖全文的分层摘要，避免为了缩短输入而遗漏必要证据。图片按任务选择分辨率和区域，文字密集内容可结合 OCR，但需要保留布局、图表和小字所需的视觉信息；视频按镜头、转录和时间段建立索引。

第二，提前处理并并行执行。文件上传后立即异步解析、分块和建立索引，尽量与用户输入问题的时间重叠。配置读取、工具候选加载和无依赖的检索可以并行；涉及权限和数据依赖的步骤仍按顺序执行。固定业务判断优先用代码完成，减少不必要的模型往返。

第三，利用缓存和快速路径。将稳定的系统指令与工具定义放在公共前缀，动态内容放在后部，提高前缀缓存命中率；预处理结果按内容版本缓存。简单问题直接进入低延迟模型，复杂问题才进入完整 Agent Loop，并保留升级路径。需要注意，首次出现的独特长输入仍需处理，缓存系统提示不能消除这部分成本。

第四，保证端到端流式显示。检查 SDK、代理、网关和前端是否及时转发、渲染增量，减少缓冲等待。复杂任务先反馈明确进度，再异步返回结果；已经验证的局部结论可以渐进展示，但进度提示不能算作真实回答 TTFT。

“稳定 2 秒”应限定输入规模、模型和并发量，以客户端有效回答 TTFT 的 p95 不超过 2 秒作为目标。分别测试冷缓存、热缓存和不同输入类型，同时验证准确率、覆盖率、总耗时与成功任务成本。自建推理还可优化预热、排队隔离和 prefill 调度。对于首次出现、必须完整理解的超大输入，需要根据计算和传输能力确定边界，并提供异步路径。

## 二 Memory

**问：和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？**

**答：**应先理解当前提问意图，再召回历史背景并检查其有效性。用户重复提问可能是想回忆上次结论，也可能是条件变化、上次没有解决问题，或希望换一种解释，因此不能匹配到相似问题后就直接返回旧答案。

存储上，将原始对话、情景记忆、用户事实与偏好、经验证经验分开管理。原始对话用于查证，情景记忆保存当时的问题、条件和结论，用户偏好用于个性化，经验用于复用方法。每条记忆记录来源消息、用户及项目作用域、发生时间、有效期、版本和可信依据，明确区分用户表达、模型推测与助手历史回答。

召回上，结合当前问题和近期上下文识别意图、实体及时间条件，先进行用户与权限过滤，再使用关键词、实体和向量混合检索。对候选进行去重、重排和冲突检查，综合考虑相关性、来源可靠性、实体一致性、时效与适用范围。主题分类主要帮助筛选和排序，候选不足时扩大召回范围，避免分类错误造成漏召回。最终只注入少量高相关记忆，并保留原文引用，关键条件回查原始对话。

时间因素需要按记忆类型处理。稳定偏好不会因半个月未提及就自然失效，行程、价格和软件版本等信息则需要有效期判断或重新查询。用户明确纠正时写入新版本并标记旧值被替代；模型自动提炼的记忆先进入候选区，经过确认或客观验证后再提高可信度，不能因频繁被检索到就认定它正确。

回答上，用户明确问“上次讨论的方案是什么”，就恢复当时结论及前提；普通重复提问则结合现状作答，利用有效背景减少重复询问。没有可靠证据时不假装记得，仅在冲突会影响结论时确认关键条件。例如，用户再次咨询 Agent 面试准备，系统应召回之前的岗位方向、薄弱模块和进度；如果岗位已变化，就沿用仍有效的信息并调整方案。

评估时覆盖原问题复现、同义改写、条件变化、过期事实、冲突事实和跨项目隔离，重点观察有效记忆召回率、误召回率、过期信息使用率、用户纠正率及检索延迟。

## 三 Task

**问：对于长程任务，大模型执行一段时间可能会忘掉目标。有哪些解决方案，有什么优缺点？**

**答：**长程任务偏航通常与上下文截断、中间信息干扰、进度未持久化和缺少验收反馈有关。推荐采用“持久化任务契约＋里程碑＋检查点＋验证器”的组合，将目标和真实进度保存在上下文之外，并在每次决策前加载必要状态。

首先，任务启动时保存原始需求、目标版本、验收标准、硬约束、里程碑、当前阶段、下一步动作、预算和产物引用。目标与计划分开管理：计划允许根据新信息调整，目标和验收条件的变化则需要用户要求或授权依据。用户修改目标后增加版本，并重新检查在途任务与已有产物。

其次，将任务拆成可验证阶段，每完成一个阶段就保存检查点，记录产物版本、工具 operation_id、已提交副作用、失败尝试及恢复位置。模型上下文保留目标、约束、未完成项、已完成证据和最新观察，大文件与完整日志放在外部存储。发生上下文压缩、服务重启或跨天恢复时，从检查点重建状态，并核对真实环境，避免重复执行已经成功的写操作。

再次，建立进展检查和重规划机制。每个阶段执行后验证是否推进目标；连续无进展、关键依赖变化或用户修改要求时触发重规划。超时、最大轮次、权限和预算由代码控制，复杂的目标相关性由阶段性模型检查辅助判断，避免每轮重新规划导致成本增加和计划抖动。

不同方案各有取舍。重复在 Prompt 中提醒目标成本最低，但无法保存真实进度；任务卡和待办清单简单清晰，但需要及时同步；持久化检查点支持暂停与恢复，但要处理版本、幂等和副作用；状态机或工作流适合固定流程，动态探索较受约束；分层规划更灵活，但增加模型调用并可能反复改计划；子 Agent 能隔离上下文、并行处理独立任务，但增加通信、依赖管理和合并成本。

实际可用外层工作流维护状态，在探索性阶段使用 Agent，在边界清晰的子任务中引入子 Agent，由主 Agent 统一维护目标并验收。代码任务通过测试和 diff 验证，配置修复通过校验报告验证，报告任务检查内容覆盖和产物质量。最终通过任务完成率、约束违反率、恢复成功率和重复执行率验证方案。

## 四 Tool / Session Runtime

**问：如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？**

**答：**应采用事件驱动、会话状态单写的机制。所有用户消息、工具完成、取消和超时事件先可靠入队，由同一 session 的协调器顺序更新状态。模型和工具可以并发执行，但完成回调不能直接修改共享对话状态。

内部应分离 session、run 和 tool job，并细分模型生成、工具执行、等待结果和等待用户等状态。事件记录 event_id、session_id、run_id 及关联调用，工具事件增加 tool_call_id、attempt、operation_id、目标版本和资源版本。协调器以短事务提交状态，发起模型或工具后释放锁，完成时通过新事件恢复；多实例通过租约与 fencing token 防止旧执行者继续提交。

对于用户新消息，按语义处理：停止和取消优先阻止后续动作，并尝试取消在途调用；修改目标或约束时保存新版本，在安全边界重规划；任务补充放入当前 run 的 inbox，在下一次相关决策前消费；独立问题默认排队，允许并行时建立隔离 run 并检查共享资源冲突；进度查询直接读取持久化快照。接收后及时反馈已接收或排队状态。模型不支持中途 steering 时，不能修改已发出的 Prompt，应在本次生成结束或取消后带入新消息。

对于异步完成事件，依次校验来源和关联关系、幂等去重、保存实际结果、检查适用性，再更新运行状态并触发恢复。有效性依据目标版本、输入依赖与资源版本判断，不能只因为会话 revision 变化就丢弃结果。取消、过期或旧 attempt 的结果也要保留，因为它们可能反映已经发生的外部副作用。

两类事件同时到达时，先记录事实与顺序，再由协调器决策。取消和关键约束变更优先阻止未来动作，但不能撤销已发生的事实。例如，工具执行期间用户要求“不要改配置，只生成报告”，系统应禁止后续写入并更新目标；工具返回后核对是否产生修改，必要时补偿，再按新目标继续。并行工具的结果可以陆续落库，恢复模型前必须满足 API 的调用与结果配对要求。

可靠性上采用至少一次投递配合幂等消费，通过事务 outbox 关联状态提交和通知。结果先可靠写入再确认，重启后恢复未完成调用和未消费事件。工具完成只代表一个步骤结束，最终通知应在 Agent 恢复并验证任务后发送。测试覆盖重复事件、乱序完成、取消后仍成功及提交后崩溃等情形，确保无事件丢失、无旧状态覆盖和无重复副作用。

## 五 Agent Runtime 架构对比

**问：Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？它们各自这样设计的优缺点是什么？**

**答：**需要先区分模型 API 协议与 Agent 执行框架。Claude Code 是带工具执行和管理能力的 Agent 产品，function calling 是模型与应用交换调用和结果的接口。因此，应先比较 Claude Messages 与 OpenAI-compatible Chat Completions，再分析 Harness 层的设计。

协议上，Claude 在 assistant.content 中使用 tool_use 块表示调用，参数 input 是对象；应用执行后，在后续 user 消息中使用 tool_result 块返回，通过 tool_use_id 关联。OpenAI-compatible Chat Completions 使用 assistant.tool_calls，function.arguments 是 JSON 字符串；应用通过 role=tool 的消息回传结果，并用 tool_call_id 关联。Claude 的 user 角色在这里是工具结果载体，不代表结果是用户指令。该比较限定为 Chat Completions，OpenAI Responses API 使用另一套调用项结构。

两类接口都支持工具参数的流式传输。Claude 使用内容块的开始、增量和结束事件，参数通过 input_json_delta.partial_json 累积，可在对应块结束后解析；Chat Completions 通常按调用 index 拼接 delta.tool_calls 中的参数，在流结束或 finish_reason=tool_calls 后确认完整集合，具体行为以提供方为准。识别到工具名可以预热资源，但实际执行需要完整参数、可靠结束边界以及 schema 和权限校验，不能因为某个片段暂时可以解析为 JSON 就直接执行。

Claude 内容块设计的优势是统一组织文本、工具及支持的其他内容，块生命周期明确，适合混合输出；代价是适配器需要处理多种事件和消息配对规则，转换到其他接口时可能有信息损失。工具结果消息需紧接对应调用消息，同一 user 消息中结果块放在普通文本前，Runtime 必须维护合法顺序。

OpenAI-compatible Chat Completions 的优势是生态广、SDK 和中间件成熟、模型切换成本相对低；代价是不同厂商对并行调用、流式分片、严格 schema 和多模态结果的支持程度不同，需要逐端点测试，不能仅凭“兼容”就认定 GLM、豆包各版本能力一致。

Claude Code 值得借鉴的工程思路在于完整执行闭环：解析、参数校验、权限与冲突控制、超时和取消、工具执行、结果结构化，以及错误反馈与恢复。大结果保存为产物，只回传摘要和引用；失败区分参数、权限、限流、网络等类别，帮助模型选择下一步。这些能力同样可以建立在兼容接口之上，但需要承担状态管理、策略维护和恢复测试成本。

实现上可增加 ModelAdapter，将不同协议转换为统一的内部工具调用，由 ToolExecutor 处理权限、依赖、幂等与执行，再将结构化观察转换回对应模型格式。适配时保留调用关联、消息顺序和必要元数据。写操作超时后先核对真实状态，再决定是否重试。最终可靠性由模型能力、工具设计、Runtime 状态管理和验证闭环共同决定。
