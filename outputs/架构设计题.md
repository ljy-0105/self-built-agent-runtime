# 架构设计题

## 一 Context / Performance

**问：大模型面对第一轮长窗口或多模态输入时，first token 会显著变慢。有什么快速、低成本、用户体验也不差的方案？如何从 5～10 秒稳定压缩到 2 秒？**

答：我会先拆一下耗时，看慢在文件解析、模型 prefill，还是工具调用和网络等待，再决定改哪里。优先做几项成本低的优化：精简首轮 Prompt，工具和 Skill 按需加载；配置读取、检索等没有依赖的步骤并行；稳定的指令和工具定义复用前缀缓存；简单问题直接走低延迟模型，减少不必要的 Agent 轮次。

长文件在上传后就开始解析和建索引，提问时只读取相关片段；全篇总结则做分层摘要，保证覆盖全文。图片按问题选择分辨率或区域，文字内容可以结合 OCR，但图表和布局信息仍需保留。网关和前端也要检查流式输出是否被缓冲。

2 秒要区分是“看到进度”还是“拿到有效回答”。首次大文件的处理成本无法靠缓存凭空消失，复杂任务可以先反馈进度、后台继续分析。验收时限定输入规模和并发量，看有效回答 TTFT 的 p95，并对比冷、热缓存下的准确率和成本，不能只把提示语提前就算达标。

## 二 Memory

**问：和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？**

答：先判断用户是在问“上次怎么说的”，还是想重新解决这个问题。两次表述相似，条件不一定相同，所以不能直接把旧答案拿出来。

召回时结合近期上下文，先按用户和权限过滤，再用关键词、实体和向量混合检索。候选记忆按相关性、来源、时间和适用范围重排，只把少量有用内容放进上下文。每条记忆保留时间和原始消息引用，关键条件能回查。用户偏好可以长期有效，行程、价格、版本等信息则要检查是否过期。

比如用户再次问怎么准备 Agent 面试，可以沿用之前的学习进度；如果岗位方向变了，就调整方案。没有可靠记录时正常回答，不假装记得。用户纠正后更新记忆，模型自己总结的内容先作为候选，不能把过去的助手回答直接当成事实。效果主要看误召回、过期信息使用和用户纠正的比例。

## 三 Task

**问：对于长程任务，大模型执行一段时间可能会忘掉目标。有哪些解决方案，有什么优缺点？**

答：我会把目标和进度存到上下文之外。任务开始时记录用户要求、验收标准、约束和待办，每轮带上当前目标、已完成事项、剩余工作和最新结果。计划可以调整，但不能为了宣布完成而改掉验收标准。

任务按阶段推进，每完成一步就保存检查点，包括产物位置、验证结果和下一步。压缩上下文或服务重启后，从检查点恢复；涉及写操作时先核对实际状态，避免重复执行。连续几轮没有进展、依赖发生变化或用户修改目标时，再触发重规划。

几种办法的取舍是：反复提醒目标最简单，但保存不了真实进度；任务卡和检查点容易落地，不过需要及时更新并处理恢复时的幂等；状态机适合固定流程，遇到开放探索不够灵活；分层规划和子 Agent 更适合复杂任务，但会增加调用、沟通和结果合并成本。

实际可以用工作流保存状态，让 Agent 处理需要判断的步骤。是否完成由证据决定，例如代码看测试，配置修复看校验报告。同时设置超时、轮次和预算上限，防止任务一直循环。

## 四 Tool / Session Runtime

**问：如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？**

答：busy 不能等同于拒收消息。我会把用户消息和工具完成都作为事件可靠入队，由同一个 session 的协调器顺序更新状态。工具可以并发执行，但多个回调不能同时改会话状态；等待工具期间也不应一直占着状态锁。

新消息分类处理：停止、取消优先响应，阻止后续动作并尝试取消在途工具；修改目标时保存新版本，在安全边界重新规划；普通补充在下一次决策前读入；独立问题默认排队。前端及时告知已收到，避免用户反复发送。

工具结果用 run_id、tool_call_id 和 attempt 关联，先去重、落库，再判断能否用于当前任务。旧结果不能覆盖新目标，但也不能直接丢弃，因为外部操作可能已经成功。例如用户要求停止改配置时，工具可能已完成写入，需要核对并决定是否回滚。

可靠性上采用至少一次投递加幂等处理，状态更新和通知通过事务 outbox 关联，崩溃后可以恢复。多个工具的结果回传还要满足模型 API 的消息配对规则。最终通知以任务验证完成为准，不能把某个工具完成当成整个任务完成。

## 五 Agent Runtime 架构对比

**问：Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？它们各自这样设计的优缺点是什么？**

答：这里需要分开看协议和执行框架。Claude Code 是 Agent 产品，function calling 是模型与应用交换工具调用的接口。协议层应比较 Claude Messages 和 OpenAI-compatible Chat Completions，后者不包括格式不同的 Responses API。

Claude 用 assistant 内容中的 tool_use 块发起调用，input 是对象；结果放在后续 user 消息的 tool_result 块，通过 tool_use_id 关联。Chat Completions 用 assistant.tool_calls 发起调用，function.arguments 是 JSON 字符串；结果通过 role=tool 的消息和 tool_call_id 返回。

两者都支持流式参数。Claude 按内容块组装，Chat Completions 按调用 index 拼接；执行都要等参数完整、调用边界明确并通过校验，不能只看到工具名就运行。Claude 内容块便于组织混合输出，但需要处理块事件和消息顺序；兼容接口生态成熟、切换模型方便，不过 GLM、豆包不同端点对并行调用、严格 schema 等能力的支持需要实测。

Claude Code 值得借鉴的主要是执行层：权限、参数校验、超时、结果大小控制和错误恢复。这些也能建立在兼容接口上。实现时用适配层统一调用和结果，执行器负责幂等与验证；大结果保存到文件，只回传摘要和引用。协议影响接入成本，能否稳定完成任务还要看工具设计和 Runtime 的恢复能力。
